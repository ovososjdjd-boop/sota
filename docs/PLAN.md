## 0. Одно предложение

Пользователь вводит сумму и состав семьи — получает недельное/месячное меню,
которое укладывается в деньги, попадает в КБЖУ, не повторяется до отвращения
и превращается в список покупок с точностью до упаковки. Без ИИ, офлайн после
первой загрузки.

## 2. Расширение идеи: что вы сказали и что из этого следует

Ваша формулировка + то, что честно нужно, но обычно забывают.

### 2.1. Ядро (ваше ТЗ)

| Требование | Как решается |
|---|---|
| Ввод суммы → меню | LP-оптимизация, бюджет как жёсткое ограничение |
| Неделя / 2 недели / месяц | Горизонт планирования — параметр |
| Попадание в КБЖУ | Нормы МР 2.3.1.2432 по каждому едоку, суммирование |
| Разнообразие | Штраф за повтор блюда, лимит частоты, ротация |
| Несколько членов семьи | Профиль на каждого: пол, возраст, вес, активность |
| Предпочтения, образ жизни | Исключения, аллергены, вегетарианство, время готовки |
| Остатки продуктов | **Учёт упаковок** — см. 2.2, это ключевое |
| Сколько тратится / в рублях | Точная смета: план vs факт покупки |
| Редактирование цен | Личный прайс поверх базового, свои продукты |
| Работа без интернета | Всё локально: SQLite/IndexedDB + WASM-солвер |
| Красивый современный UI | См. раздел 5 |

### 2.2. Что критично и обычно упускают

**Проблема упаковок.** Оптимизатор говорит «1.41 кг гречки». В магазине гречка
по 800 г. Купишь 2 пачки = 1.6 кг, останется 190 г. Через месяц у тебя шкаф
недоеденных остатков, а бюджет уехал на 15%.

Решение: двухслойная модель.
- **Слой 1 (непрерывный):** сколько грамм нужно съесть — LP.
- **Слой 2 (целочисленный):** сколько упаковок купить — MILP с переносом
  остатка на следующий период. Остаток — не мусор, а актив следующей недели.

Это отличает игрушку от инструмента.

**Проблема порчи.** Молоко 4 кг на неделю — испортится. Каждому продукту:
срок хранения, темп расхода, флаг «скоропорт». Оптимизатор не имеет права
запланировать то, что сгниёт.

**Проблема «математически идеально, есть невозможно».** LP найдёт оптимум из
картошки с маслом. Нужны кулинарные ограничения: завтрак ≠ борщ, белок в каждом
основном приёме, минимум N разных блюд в неделю, овощи ежедневно.

**Проблема доверия.** Пользователь должен видеть, *почему* так. Каждое решение
объясняется: «гречка потому что 12.6 г белка за 120 ₽/кг — лучший белок на рубль
в вашем списке».

**Проблема холодного старта.** Первый экран не должен требовать 40 полей.
3 вопроса → результат → потом уточняй.

### 2.3. Что я предлагаю добавить

1. **Режимы оптимизации** — не только «влезть в бюджет», но и:
   - минимум денег при заданном КБЖУ (сколько минимально нужно?)
   - максимум качества рациона при заданных деньгах
   - минимум времени готовки
2. **Готовка партиями (batch cooking)** — сварил кастрюлю на 3 дня. Резко
   снижает время и стоимость.
3. **Инфляционный пересчёт** — цены Росстата отстают на месяц; индексируем по ИПЦ.
4. **Экспорт** — PDF-меню на холодильник, список покупок в телефон, ICS-календарь.
5. **Режим «что у меня уже есть»** — инвентарь дома, план учитывает запасы.
6. **Сравнение сценариев** — «а если 3000 вместо 2000?» бок о бок.

## 3. Архитектура

### 3.1. Принципиальное решение: локальное приложение

Всё считается на устройстве. Причины: работает офлайн (ваше требование),
нет серверных расходов, персональные данные о питании никуда не уходят,
нет юридических вопросов про обработку ПД.

```
┌─────────────────────────────────────────────────────┐
│  UI (React + TypeScript + Vite)                     │
│  Онбординг · Меню · Смета · Покупки · Прайс         │
├─────────────────────────────────────────────────────┤
│  Движок (чистый TS, без зависимостей от UI)         │
│  ├── nutrition/   нормы КБЖУ по профилям            │
│  ├── optimizer/   LP: продукты под КБЖУ и бюджет    │
│  ├── packaging/   MILP: упаковки, остатки, перенос  │
│  ├── menu/        сборка блюд, разнообразие         │
│  └── explain/     почему такое решение              │
├─────────────────────────────────────────────────────┤
│  HiGHS (WASM)  ·  ~1 МБ  ·  проверен, 47 мс         │
├─────────────────────────────────────────────────────┤
│  Данные (локально, версионированы)                  │
│  products · prices · recipes · norms · user_prices  │
└─────────────────────────────────────────────────────┘
```

Стек: React + TypeScript + Vite + Tailwind. PWA — ставится на телефон,
работает без сети. Позже при желании — обёртка в десктоп/мобильное приложение.

### 3.2. Математическая модель

**Переменные:** `x_i` — граммы продукта i за период; `y_j` — упаковок j (целое);
`z_d,m` — блюдо m в день d (бинарное).

**Ограничения:**
```
Энергия/БЖУ:   L_n ≤ Σ x_i · nutrient(i,n) ≤ U_n     для каждого нутриента
Бюджет:        Σ y_j · price_j ≤ B                    жёстко
Упаковки:      Σ y_j · size_j ≥ x_i - stock_i         купить не меньше, чем съесть
Порча:         x_i ≤ shelf_life_i · daily_rate_i      скоропорт под контролем
Разнообразие:  Σ_d z_d,m ≤ max_freq_m                 не есть одно и то же
Структура:     Σ_m z_d,m · is_protein_m ≥ 1           белок каждый день
Предпочтения:  x_i = 0                                для исключённых
```

**Целевая функция** (взвешенная сумма, веса настраиваются):
```
min  w1·|отклонение КБЖУ| + w2·(остатки) + w3·(монотонность) - w4·(предпочтения)
```

Всё линейно ⇒ HiGHS решает точно и быстро. Модули по 200 продуктов и
14 дням — оценочно доли секунды; замерю на реальных данных.

### 3.3. Данные

```
data/
├── products/      ~300-500 базовых продуктов: КБЖУ, категория,
│                  срок хранения, типовые фасовки, коэф. ужарки
├── prices/        цены Росстата по регионам + дата среза
├── recipes/       ~200 блюд: раскладка, время, сложность, приём пищи
└── norms/         МР 2.3.1.2432: нормы по полу/возрасту/активности
```

Каждая запись с полем `source` — откуда взята. Проверяемо.

| Источник | Лицензия | Что делаем |
|---|---|---|
| Росстат | Открытые данные, госстатистика | Используем, указываем источник и дату |

**Чего НЕ делаем:** не парсим сайты магазинов (нарушение ToS + юридический риск),
не копируем чужие базы рецептов с авторскими текстами, не выдаём медицинские
рекомендации.

**Дисклеймер в продукте:** приложение — инструмент планирования бюджета, не
замена консультации врача или диетолога. Обязателен, особенно при наличии
пресетов вроде «набор массы» или «дефицит калорий».

## 5. UI: «которым хочется пользоваться»

**Принцип:** это приложение про деньги и еду — значит цифры должны быть
крупными и понятными, а еда должна выглядеть аппетитно.

**Первый экран.** Одно поле — сумма. Крупно. Один вопрос — на скольких человек.
Кнопка «Составить». Всё. Настройки — потом, когда уже видно результат.

**Главный экран — календарь-сетка.** Неделя по горизонтали, приёмы пищи по
вертикали. Каждая карточка: название, ккал, цена. Сверху — «живой» бюджет-бар:
потрачено / осталось, меняется при правках в реальном времени.

**Ключевая фишка — прямое редактирование.** Не нравится блюдо — свайп, замена
на равноценное по КБЖУ и цене. Пересчёт мгновенный (47 мс это позволяет).
Ощущение: ты управляешь, а не смотришь на выданное.

**Экран сметы.** Куда ушли деньги — по категориям, наглядно.
Список покупок — по отделам магазина, с чекбоксами, в упаковках, с ценой.

**Экран КБЖУ.** Кольца-прогресс на день и на неделю. Зелёный/жёлтый/красный.

**Визуальный язык:** светлая база, один сочный акцентный цвет,
крупная типографика для цифр, скруглённые карточки, мягкие тени,
плавные анимации пересчёта. Тёмная тема. Мобильный приоритет.

**Что делает интерфейс живым:** анимация числа при пересчёте бюджета,
отклик на каждое действие, объяснение решений при тапе на карточку,
нулевое ожидание — всё локально.

## 6. План работ

Я предлагаю делать **вертикальными срезами** — на каждом этапе есть
работающий продукт, который вы можете открыть и потрогать. Не «три недели
бэкенда, потом посмотрим».

### Этап 0 — Фундамент (первый)
Репозиторий, TypeScript, Vite, CI, структура папок, HiGHS подключён и покрыт
тестом. **Результат:** `npm run dev` открывает пустое, но живое приложение.

### Этап 1 — Данные
Сбор ~300 продуктов с КБЖУ, ценами Росстата, фасовками, сроками хранения.
Нормы МР 2.3.1.2432. Схема + валидация + указание источников.
**Результат:** проверяемый датасет в репозитории.

### Этап 2 — Движок КБЖУ и оптимизатор
Расчёт норм по профилю (Миффлин-Сан Жеор + коэффициент активности,
сверка с МР). LP-оптимизация корзины. Юнит-тесты на граничные случаи:
крошечный бюджет, огромная семья, жёсткие ограничения.
**Результат:** CLI — вводишь параметры, получаешь корзину.

### Этап 3 — Упаковки и остатки
MILP-слой, перенос остатков между периодами, контроль порчи.
**Результат:** список покупок в реальных пачках, а не в абстрактных граммах.

### Этап 4 — Меню из блюд
База рецептов, раскладка продуктов в блюда по дням, разнообразие,
структура приёмов пищи, batch cooking.
**Результат:** настоящее меню на неделю.

### Этап 5 — UI
Онбординг, календарь меню, бюджет-бар, смета, список покупок,
редактор цен, профили семьи, объяснения решений.
**Результат:** то, чем хочется пользоваться.

### Этап 6 — Полировка
PWA/офлайн, экспорт PDF/ICS, тёмная тема, доступность, производительность,
сценарии сравнения.

### Этап 7 — Проверка на реальности
Прогон на настоящих бюджетах: 5 000 ₽ на одного, 20 000 ₽ на семью из 4,
студенческие 3 000 ₽. Проверка, что меню съедобное и цены сходятся с магазином.
